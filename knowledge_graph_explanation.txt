THE BIG PICTURE
===============

You're building an AI system that looks at drone footage of a home's defensible space
and automatically checks whether it complies with California fire law (PRC 4291) and
IBHS wildfire standards. The knowledge graph is the regulatory brain of that system —
it encodes every rule, every object, every zone, and every possible violation in a
structured, queryable form so a Vision-Language Model (VLM) can receive precise,
regulation-grounded prompts.

Pipeline flow:

    Drone image → Detect object (e.g. "propane tank") + zone (e.g. "Zone_0")
                          ↓
                query knowledge graph
                          ↓
        "Zone_0 + propane → PRC 4291(d) → IBHS_Z0_003 → violation: Propane_within_5ft → CRITICAL"
                          ↓
            VLM receives this context as a structured prompt
                          ↓
            "This propane tank is within 5 ft of the structure. CRITICAL violation of PRC 4291(d)."

STEP 2 — prc4291_raw.txt and prc4291_sections.json
======================================================================

WHAT IT IS:
California Public Resources Code Section 4291 — the actual state law that mandates
defensible space around homes in fire-prone areas.

HOW IT WAS FETCHED:
The script makes a live HTTP request to law.justia.com. If the fetch fails or returns
too little text, it falls back to an embedded full copy of the statute so the pipeline
never breaks.

FILE: prc4291_raw.txt (11 KB)
  The raw statutory text exactly as fetched. This is the evidence file. If anyone asks
  "where did this come from?", this is it.

FILE: prc4291_sections.json (7.3 KB)
  The statute broken into 15 individual sub-sections. Each entry:

    {
      "section_id": "PRC_4291_1A",
      "full_text": "Remove all combustible material, including wood fencing, bark or
                    wood chip mulch, combustible ground cover, dead vegetation within
                    5 feet of the building...",
      "zone_scope": "Zone_0",
      "requirement_type": "removal"
    }

  The parser extracts:
    - (a), (b) letter subsections     → PRC_4291_A, PRC_4291_B
    - (1), (2) number subsections     → PRC_4291_1, PRC_4291_2
    - (1)(A), (1)(B) compound items   → PRC_4291_1A, PRC_4291_1B

  zone_scope is INFERRED from text:
    - "5 feet"       → Zone_0
    - "5-30 feet"    → Zone_1
    - "30-100 feet"  → Zone_2

  requirement_type is also inferred:
    - removal / clearance / maintenance / structural

WHY THIS MATTERS:
These become regulation nodes in the graph. Every object that is mentioned (or implied)
by a PRC section gets a directed edge to it, so when your VLM asks "what law governs
this firewood pile?", the graph returns the exact statutory text.

STEP 3 — ibhs_requirements.json
======================================================================

WHAT IT IS:
248 individual requirements extracted from WFPH-Technical-Standard.pdf
(Insurance Institute for Business & Home Safety, 2025 edition, 15 pages).

HOW IT WAS PARSED:
pdfplumber reads all 15 pages. The text is split into chunks at bullet points and
paragraph breaks. Each chunk is analyzed with regex and keyword matching to produce:

    {
      "ibhs_id": "IBHS_Z0_003",
      "zone": "Zone_0",
      "requirement_text": "Propane tanks within 5 feet of structure — not permitted.
                           Must be relocated outside Zone_0.",
      "object_mentions": ["propane_tank"],
      "aerial_detectable": true,
      "requirement_type": "removal",
      "severity": "CRITICAL"
    }

BREAKDOWN OF 248 REQUIREMENTS:
  - 239 parsed directly from the PDF text (raw extraction)
  - 9   hand-curated requirements added to ensure the most critical Zone_0/Zone_1/
        Zone_2 rules are present even if the PDF parser missed them

THE aerial_detectable FLAG — KEY FIELD (Novelty Claim N5):
  - True  : the requirement involves a physically visible object
             (propane tank, vehicle, firewood, deck, furniture)
  - False : requires ground inspection
             (vent mesh size, wall material rating, door gap measurements, soffit lining)

SEVERITY ASSIGNED BY ZONE:
  - Zone_0 → CRITICAL
  - Zone_1 → HIGH
  - Zone_2 → MEDIUM

WHY THIS MATTERS:
These become the primary regulatory nodes your VLM queries. An IBHS requirement is
much more specific and actionable than a PRC statute — it tells you exactly what to
check (e.g., "woodpile must be at least 30 ft from home"), not just a general clearance
mandate.

HOW THE FUZZY MATCHING WORKS
------------------------------

For every object–regulation pair, a confidence score (0.0–1.0) is computed:

  Match type                  | Score | Example
  ----------------------------|-------|-----------------------------------------------
  Exact name in reg text      |   1.0 | "propane" in IBHS text saying "propane"
  Alias match                 |   0.8 | "lpg" matches propane alias list
  Category match              |   0.6 | "combustible materials" → all combustibles
  Zone inference              |   0.4 | object in Zone_0, regulation covers Zone_0

Confidence score distribution across all edges:
  1.0 :   52 edges  (0.6%)
  0.8 :  160 edges  (1.8%)
  0.6 : 1876 edges  (21.6%)
  0.4 : 6591 edges  (75.9%)

STEP 8 — GRAPH EXPORT FILES AND graph_rag_lookup.py
======================================================================

FILE: knowledge_graph.graphml (1.2 MB)
  The full graph serialized in GraphML format — an XML-based standard that can be
  loaded by NetworkX, Gephi, Cytoscape, or any graph analysis tool.

  To reload in any future notebook:
    import networkx as nx
    G = nx.read_graphml("knowledge_graph.graphml")

FILE: knowledge_graph_nodes.json (111 KB)
  Every node with all its attributes as a JSON array. This is what the RAG lookup
  reads at runtime — no need to reload the full graph for each query.

FILE: knowledge_graph_edges.json (1.0 MB)
  Every edge with source, target, relation type, and confidence score. Together with
  nodes.json, this is a complete portable representation of the graph that any system
  can consume without requiring NetworkX.

FILE: graph_rag_lookup.py (6.3 KB)
  The interface between your knowledge graph and the VLM. A self-contained Python
  module with one primary function:

    def get_regulatory_context(object_class: str, zone: str) -> dict

  WHAT IT RETURNS:
    {
      "object_class"      : "propane",
      "zone"              : "Zone_0",
      "zone_range"        : "0-5 ft (Immediate Noncombustible Zone)",
      "prc_sections"      : [...],   # all matching PRC 4291 sections
      "ibhs_requirements" : [...],   # all matching IBHS reqs, sorted by confidence
      "violations"        : [...],   # all violation types this object can cause
      "aerial_detectable" : True,
      "vlm_prompt"        : "A Propane detected in Zone_0 (0-5 ft). ..."
    }

  THE vlm_prompt FIELD:
  A ready-to-inject text fragment for your VLM's system prompt. When a drone detects
  a propane tank in Zone_0, you call:

    ctx = get_regulatory_context("propane", "Zone_0")
    vlm_input = ctx["vlm_prompt"]

  And inject vlm_input directly into the VLM context so the model has regulatory
  grounding for its compliance assessment. Example output:

    "A Propane detected in Zone_0 (0-5 ft (Immediate Noncombustible Zone)).
     Applicable regulation: propane/LPG storage tanks shall be kept free of
     combustible material for a distance of at least 10 feet around the base.
     IBHS requirement: Propane tanks within 5 feet of structure — not permitted.
     Compliance assessment required: Propane_within_5ft.
     Severity if non-compliant: CRITICAL."

  ALIAS RESOLUTION:
  The function automatically resolves synonyms — so
    get_regulatory_context("firewood", "Zone_1")
  maps to the woodpile object class without you needing to use the canonical name.
